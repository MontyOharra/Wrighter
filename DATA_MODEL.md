# Wrighter — Data Model & Persistence Design

Status: **draft.** Derived from `REQUIREMENTS.md` (read that first). Picks the storage substrate,
the entities/tables, the revert + fork mechanics, the migration/versioning setup, and the server
API surface. Schema shown as logical tables — exact Drizzle definitions land in `server/` when we
scaffold.

---

## 1. Storage substrate

- **One `.wrighter` file per project.** A self-contained SQLite database. Opened by the server
  process (Hono today; the same code becomes the Electron main process later). **One project open
  per app instance** — multiple projects open at once (terminal-tab style) is a later concern.
- **Driver / ORM / migrations:** `better-sqlite3` + Drizzle ORM + `drizzle-kit`. Migration SQL is
  generated by `drizzle-kit` from schema changes and checked into the repo under
  `server/drizzle/`.
- **Schema versioning:** each `.wrighter` file records its schema version (SQLite's
  `PRAGMA user_version`, plus whatever bookkeeping table Drizzle uses). **Migrate-on-open:**
  opening a project reads the version, applies any pending migrations forward in a transaction,
  bumps the version. New project = run all migrations on a fresh file. Migrations are
  forward-only and must never assume a fresh DB.
- **App-global config** (recent-projects list, user prefs, last-opened) lives **outside** every
  `.wrighter` file — a small JSON file (or its own tiny SQLite) in the user's config dir. A
  `.wrighter` file is portable and self-contained; it never references app state or other files.

## 2. Identity & conventions

- **Primary keys:** UUIDv4 strings, client-generatable (plays nicely with the eventual IPC
  transport and any future sync).
- **Timestamps:** integer epoch-milliseconds (SQLite has no native datetime type). Columns named
  `*_at`.
- **Ordering within a node's message log:** a monotonic integer `seq` per node (1, 2, 3, …).
  Checkpoints are addressed as `(node_id, seq)` — no separate checkpoint table; every message
  *is* a checkpoint.
- **Enums** are stored as short text (`'idea'`, `'pending'`, …) with a CHECK constraint, not
  integers — readability over micro-optimization.
- **Soft state vs hard delete:** rows are only ever hard-deleted when their subgraph is marked
  inactive *and then* deleted (R3.7), or when a revert discards them (R6.2). Everything else is a
  status transition.

## 3. Entities

### `project` — single row
The file *is* the project, so this is a one-row table holding project-level metadata.

| column | type | notes |
|---|---|---|
| `id` | uuid PK | |
| `name` | text | mirrors the root node's `title` (R2.5) — kept here too for cheap reads |
| `root_node_id` | uuid → node | the one root idea node |
| `created_at` / `updated_at` | int | |

### `node`
| column | type | notes |
|---|---|---|
| `id` | uuid PK | |
| `parent_id` | uuid → node, nullable | the **canonical tree** (R3.2). Null only for the root. |
| `type` | text | `'idea'` for V0; model must not assume it's the only one (R3.1) |
| `title` | text, nullable | ordinary attribute, not structurally required (R3.9) |
| `state_json` | text (JSON) | structured node state — summary, purpose, open questions, considerations, per-type fields (R4.5). JSON blob because the shape varies by type and V0 has only `idea`; revisit if it bites. |
| `alternative_group_id` | uuid → alternative_group, nullable | **null for the vast majority of nodes.** Set only when this node is a competing candidate for a slot (R3.5/R3.6). |
| `active` | int (bool) | false ⇒ this node is in an inactive subgraph (R3.7), invisible to the orchestrator. **Denormalized onto every node**; toggling writes it across the whole subtree. |
| `canvas_x` / `canvas_y` | real | position in the graph view |
| `created_by` | text | `'user'` or `'orchestrator'` (R3.3/R3.4) |
| `created_at` / `updated_at` | int | |

> Pending (proposed-but-not-confirmed) nodes do **not** live here — they're rows in `proposal`
> until accepted (see §3 `proposal` and Fork B in the design notes).

### `edge` — *lateral edges only*
The tree is `node.parent_id`. This table is for non-tree links: the weighted shortcut/portal
edges (R3.8) and any future manual user-set links. Empty in V0; the table exists from day one so
the V1 propagation layer has somewhere to write.

| column | type | notes |
|---|---|---|
| `id` | uuid PK | |
| `source_node_id` / `target_node_id` | uuid → node | |
| `kind` | text | `'shortcut'` (orchestrator-built) \| `'manual'` (user-set) |
| `weight` | real | accumulates as the edge proves load-bearing (R3.8); ~1.0 initially |
| `created_by` | text | `'orchestrator'` \| `'user'` |
| `created_at` / `updated_at` | int | |

### `alternative_group`
A set of sibling candidates filling one slot, with one marked selected (R3.5/R3.6).

| column | type | notes |
|---|---|---|
| `id` | uuid PK | |
| `label` | text, nullable | e.g. `"database engine"` |
| `selected_node_id` | uuid → node | which candidate is currently the chosen one |
| `created_at` / `updated_at` | int | |

Invariant: every `node` with `alternative_group_id = G` shares the same `parent_id`; exactly one
of them is `G.selected_node_id`.

### `message` — the full-fidelity conversation log (R4.1)
Append-only. The source of truth for a node's conversation; never summarized, never lossy.

| column | type | notes |
|---|---|---|
| `id` | uuid PK | |
| `node_id` | uuid → node | |
| `seq` | int | monotonic per node; ordering + checkpoint address |
| `role` | text | `'user'` \| `'assistant'` \| `'system'` |
| `content` | text | |
| `provider_session_id` | text, nullable | the agent-SDK session this turn belonged to — debugging only; not load-bearing across restarts (sessions don't survive a process restart; the active context is rebuilt instead) |
| `created_at` | int | |

### `active_context` — the derived working window (R4.2/R4.3)
One row per node. The compacted view actually fed to the node agent: a rolling summary of the
older span + a pointer to where the raw tail begins. Regenerated as the conversation grows;
losing it loses nothing (rebuildable from `message`).

| column | type | notes |
|---|---|---|
| `node_id` | uuid → node, PK | one per node |
| `summary` | text | rolling summary of messages before `tail_from_seq` |
| `tail_from_seq` | int | messages with `seq ≥` this are included raw |
| `updated_at` | int | |

### `decision` (R4.4, R5.1–R5.2)
A settled design choice, user-authored / agent-proposed. *Proposed* decisions live in `proposal`
until accepted; a row appears here only once committed.

| column | type | notes |
|---|---|---|
| `id` | uuid PK | |
| `node_id` | uuid → node | the node it belongs to |
| `content` | text | the decision statement |
| `status` | text | `'committed'` \| `'discarded'` (set when a revert kills it, R6.2) \| `'superseded'` |
| `supersedes_decision_id` | uuid → decision, nullable | when a re-decision replaces an earlier one |
| `committed_at` | int | |

### `decision_source` — join (R5.2)
Which messages a decision derived from. Many-to-many: `(decision_id, message_id)`.

### `proposal` — the unified confirmation inbox (R3.4, R7)
Everything an agent suggests that needs the user's OK. Accepting a proposal materializes the real
row (a `node`, a `decision`, or applies a node-state update); the proposal row stays as a record.

| column | type | notes |
|---|---|---|
| `id` | uuid PK | |
| `kind` | text | `'new-node'` \| `'node-update'` \| `'decision'` |
| `payload_json` | text (JSON) | the proposed change — shape depends on `kind` |
| `target_node_id` | uuid → node, nullable | for `node-update` (which node) / `new-node` (parent) / `decision` (which node) |
| `status` | text | `'pending'` \| `'accepted'` \| `'rejected'` |
| `proposed_by` | text | `'orchestrator'` \| `'node-agent'` |
| `created_at` / `resolved_at` | int | |

> Excluded from the proposal gate (R7): orchestrator-built `edge` rows (autonomous), and
> `active_context` compaction (working-window management). Those write directly.

### `propagation` — what changed because of a decision (R5.4, R6.3)
Records that committing a decision caused an update to a node. When that decision is later
discarded/superseded, these rows tell the orchestrator which nodes to revisit.

| column | type | notes |
|---|---|---|
| `id` | uuid PK | |
| `decision_id` | uuid → decision | the cause |
| `affected_node_id` | uuid → node | what got updated |
| `update_summary` | text | brief description of the change applied |
| `created_at` | int | |

## 4. Revert mechanics (R6.1–R6.4)

`revert(node, N)` — restore node's conversation to checkpoint `seq = N`:

1. **Hard-delete** `message` rows in `node` with `seq > N`. *(Discard, per R6.2. If we ever want
   git-reflog-style "undo the revert", switch this to a tombstone flag — clean upgrade path.)*
2. Find `decision` rows in `node` whose `decision_source` references any deleted message; set
   them `status = 'discarded'`. For each, collect its `propagation` rows' `affected_node_id`s.
3. Regenerate `node`'s `active_context` from the surviving message log.
4. Enqueue an orchestrator pass over `{node} ∪ affected nodes`. The orchestrator does **forward
   re-propagation** — it re-examines those nodes given the changed decision set and proposes
   updates as normal (R6.3). It does **not** rewind anything elsewhere; we never reconstruct old
   graph structure.

No whole-graph snapshots, no graph-mutation event log — `message` + `decision` + `propagation` is
sufficient (R6.3).

## 5. Fork mechanics (R3.5)

`fork(source, mode)` — create a competing alternative for the slot `source` occupies:

1. If `source.alternative_group_id` is null, create an `alternative_group` G with
   `selected_node_id = source.id` and set `source.alternative_group_id = G`.
2. Create a new `node` N: same `parent_id` as `source`, `alternative_group_id = G`,
   `active = true`, `created_by = 'user'`. The group's selected candidate is unchanged (still
   `source`) unless the user promotes N.
3. `mode = 'clean'`: N starts with an empty message log, no decisions, fresh `active_context`.
   `mode = 'copy'`: duplicate `source`'s `message` rows into N (new ids, same `seq` order); copy
   `source`'s `committed` decisions into N, remapping `decision_source` to the copied messages;
   copy `active_context`.
4. The subtree *below* `source` is **not** copied. Both `source` and N stay active.

`selectAlternative(group, node)` — set `group.selected_node_id = node`. Direct user action. The
user will typically then `deactivate` the losing candidates' subtrees (§6) once the choice is
settled.

## 6. Server API surface

REST-ish over the Hono server today; the same call shapes become IPC handlers inside Electron
later (per ADR 0012 — call sites don't change). Streaming endpoints use SSE, as `/forge/idea`
does today.

| area | endpoint | notes |
|---|---|---|
| project | `POST /project` | create = create the root idea node (title + framing) |
| | `GET /project` | project metadata + the full graph (nodes, edges, alternative groups) |
| | `PATCH /project` | rename → updates the root node's `title` and `project.name` |
| nodes | `POST /nodes` | create an ordinary child (R3.3) — `{ parentId, type, title? }` |
| | `PATCH /nodes/:id` | edit `title` / `state_json` / canvas position |
| | `POST /nodes/:id/fork` | `{ mode: 'clean' \| 'copy' }` (R3.5) |
| | `POST /nodes/:id/select` | make this node its alternative group's selected candidate |
| | `POST /nodes/:id/deactivate` · `POST /nodes/:id/activate` | toggle the subtree's `active` flag |
| | `DELETE /nodes/:id` | only if the subtree is inactive (R3.7) |
| | `POST /nodes/:id/revert` | `{ seq }` (§4) |
| conversation | `GET /nodes/:id/messages` | the full log |
| | `POST /nodes/:id/messages` | send a turn → SSE-streams the node agent's reply (the generalized `/forge/idea`) |
| proposals | `GET /proposals` | pending inbox (R7) |
| | `POST /proposals/:id/accept` · `POST /proposals/:id/reject` | accept materializes the real row |
| edges | `GET /edges` | lateral edges for rendering — empty in V0 |
| orchestrator | `GET /orchestrator/status` | for the UI's "thinking" indicator; the orchestrator itself is internal, triggered after decision-commit / node-create |

## 7. Migration / versioning setup

- `drizzle-kit generate` produces SQL migration files under `server/drizzle/`, checked into git.
- On project open: open the file → check the schema version → apply pending migrations in order
  inside a transaction → bump the version.
- On new project: create the file → run all migrations from scratch.
- Migrations are forward-only, ordered, and never assume a fresh DB. Destructive changes
  (dropping/renaming columns) get the careful multi-step treatment.

## 8. Not in the data model (deferred — see `REQUIREMENTS.md` §8)

- Embeddings / vector index (`sqlite-vec`) — known-temporary deferral; no hard dependency, but
  leave room (an `embedding` blob column + a vec virtual table can be added later without
  reshaping anything).
- Whole-graph snapshots / graph-mutation event log — not needed (revert is forward re-propagation).
- The weighted shortcut-edge *traversal/reinforcement logic* — V1; the `edge` table exists now,
  unused.
- Manual user-set links — table supports `kind = 'manual'`, but the UX is V1+.
- Cross-project references; branch-merge; multi-project-open; reflog-style un-revert.
- A graph database (Neo4j/KuzuDB) — V2+ "if propagation over large graphs gets slow"; the likely
  move then is an in-memory graph index over SQLite, not a DB swap. KuzuDB (embedded) is the one
  to evaluate if a swap is ever warranted.

## 9. Open questions for this layer

- **`active_context` shape.** V0: a single `summary` string + `tail_from_seq`. Is one summary
  layer enough, or do long conversations want hierarchical/multi-layer compaction? Revisit when
  it's not enough.
- **`proposal.payload_json` schemas per `kind`.** Needs nailing down alongside the orchestrator
  build — what exactly a `node-update` proposal carries, etc.
- **Concurrent orchestrator runs.** Decision-commits and node-creates can pile up; does the
  orchestrator queue serially per project, or coalesce? V0: serial queue per project, probably.
- **`canvas_x/y` authority.** Stored server-side, or purely client layout state? Leaning
  server-side so the layout persists with the project — confirm.
